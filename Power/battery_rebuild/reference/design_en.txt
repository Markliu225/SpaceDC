13 [Heading 1] Document Overview
14 [Heading 2] Purpose
15 [Normal] This report specifies the power model for a computing node on one satellite. Its physical components are a solar array, battery pack, power controller, and distribution unit. Orbit illumination and computing demand determine solar generation, battery charging or discharge, delivered power, and battery and distribution heat. A reduced single-particle model, SPM, retains one average lithium state per electrode and couples to the lumped battery temperature in Thermal.
16 [Heading 2] Scope
17 [Normal] The report defines equations, module responsibilities, interfaces, and scene configuration for preparing component parameters and implementing the solver. Asset fields and model bindings are proposed project interfaces; they do not imply implementation in the existing demonstrator. The scene specifies the target cell and its electrochemical parameter set. Capacity and operating C-rate follow the selected cell parameters.
18 [Heading 2] Intended readers
19 [Normal] The report is for Power developers, Thermal and Compute integrators, and researchers preparing device parameters and configuring simulation scenes. Chapter 4 defines the physical model, Chapter 5 explains its functions, and Chapter 6 specifies their calling contracts.

51 [Normal] Internal battery heat, , is sent to Thermal. Equation P1 already uses battery-terminal electrical power, so internal heat is not deducted again. This version neglects controller losses and uses fixed solar-array and distribution efficiencies, while retaining battery electrochemical and temperature coupling. Radiation does not affect this model.
52 [Normal] This version combines continuous state equations with algebraic relations. Power owns two continuous states: average lithium fractions in the negative and positive electrodes. Current determines the lithium-transfer rate and thus their time evolution. Terminal voltage, surface fractions, solar output, and component heat are evaluated from the current state without separate integration states.
53 [Normal] Battery temperature belongs to Thermal. Temperature changes diffusion, reaction kinetics, and voltage, which change the current and heat required for the same demand. Battery heat then affects temperature, forming the coupling between Power and Thermal. Calculations use states at the same time. Section 8 explains how the solver avoids holding an outdated temperature during battery evaluation.
54 [Normal] The array uses fixed maximum-power-point efficiency, the controller ideal quasi-static MPPT, and the distribution unit fixed efficiency. These support orbit-scale energy and supply calculations. Switching waveforms, bus capacitance, and voltage ripple are outside this model. The battery uses the literature's quadratic particle-concentration approximation, retaining electrode material and reaction parameters without spatial electrolyte discretization. [1–4]

120 [Heading 2] Overall Power-System Evaluation
121 [Normal] This function is the Power entry point used by the coupled calculations in Section 3.3. It solves the solar-array, battery, controller, and distribution models together and returns results for the complete power system.
122 [Normal] The function calls solar_power and determines actual demand from state.load_connected. For a connected load, P3 gives required bus power. Establish the admissible interval from zero current in the charging or discharge direction to the first device constraint, and call battery_response to find the first feasible solution of P11. Each trial recomputes surface fractions, material functions, and voltage. Current error and power residual are checked separately using parameters.numerics. Controller loss is neglected; P3 divides bus input into P_load_W and Q_D_W.
123 [Normal] When solar surplus reaches a charging limit, evaluate battery power at the permitted current and use P1 to select actual P_pv_W. A disconnected load keeps zero bus and load powers while solar charging continues. To assess a new start command, also check whether the current request could be connected and return can_supply_request without changing the switch. A normal result includes the four domain ports, both lithium derivatives, and battery diagnostics.
124 [Normal] A supply-loss condition requires device-boundary calculations confirming insufficient capability. This assessment checks available terminal power over the admissible current interval, not merely whether its endpoints bracket a root. event_required=True means that the boundary must first be located and accepted. A trial neither latches a trip nor provides a valid result for integration across that boundary. After acceptance, apply Section 5.6 and reevaluate at the same time. Missing a valid bracket or failing numerical convergence returns a numerical failure and reason; neither automatically means insufficient supply. Undefined powers and derivatives remain empty when no valid operating result exists.
125 [Heading 2] State Update at Accepted Events
126 [Normal] This function implements the load-switching and supply-loss protection updates in Section 4.5. Simulation calculations call it after accepting an event boundary. It uses the overall evaluator's decision; the caller then reevaluates supply after the update.
127 [Normal] state contains lithium states accepted at the event time, event is an accepted start, stop, or supply-loss event at that time, and decision is its PowerResult. Check time, instance, and identifier, then return a new PowerState while preserving x_n and x_p. Reject trial events with accepted=False or error results with decision.valid=False, and do not execute a command identifier twice. supply_loss also requires confirmation of its physical boundary in the result; an ordinary numerical error cannot create that event.
128 [Normal] stop disconnects the load. supply_loss disconnects it and latches the trip. A new start connects and clears the latch only when decision.can_supply_request=True; otherwise it remains disconnected. Simultaneous stop or supply loss takes priority over start, without repeated automatic retries. Reevaluate powers and heat at that time, then continue integration. Continuous trial stages use pure evaluation and do not call this function to change protection state.

172 [Normal] Archive asset and model versions, resolved parameters, initial conditions, orbit epoch, workload, and solver tolerances for every run. Thermal alone updates Battery01 temperature, and SolarArray01 does not use Orbit's older thermal integrator. Actual solar electricity must not exceed compatible absorbed solar energy. Initial zero-current voltage and temperature must lie within the parameter set's applicable ranges.
173 [Normal] initial_state_fields contains run and instance identifiers, initial time_s, x_n, x_p, initial load_connected, trip_latched, and empty handled_command_ids. Two instances of one battery asset receive separate fields. After an accepted integration result, write new lithium states and time into accepted_state_fields. Preserve the discrete fields until apply_power_event processes an accepted event.
174 [Heading 1] Limitations and Planned Evolution
175 [Normal] The baseline supports supply studies for one computing node within a satellite, retaining battery electrochemistry, temperature, and load-delivery feedback. Solar temperature does not alter the fixed array efficiency, and radiation does not change power parameters. Identical cells and uniform pack temperature omit cell imbalance, aging, and thermal runaway.
176 [Normal] Add particle-diffusion states when fast pulses or diffusion relaxation must be resolved; consider SPMe or reduced DFN when electrolyte gradients matter. Changes to the battery's internal solver can retain external current, voltage, power, heat, and temperature interfaces. Bus transients or switching design require an additional circuit model.
