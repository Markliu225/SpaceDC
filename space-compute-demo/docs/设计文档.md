# space-compute-demo 设计文档

## 1. 设计目标与原则

**目标**：用一套"Web 主 UI + Omniverse 流式三维 + Python 物理引擎"的三段式架构，做一个可对外演示的 1MW 级太空数据中心数字孪生。

**核心设计原则**：

1. **单一权威源 (Single Source of Truth)**
   后端 `StateEngine` 是业务状态的唯一权威。Web 不做任何物理推导，只插值显示；Kit 不做业务计算，只把当前状态投影到 USD prim 上。
2. **Web 是主 UI，三维只是嵌入**
   Web 主导路由、参数面板、图表；三维视口是页面上的一个矩形坑。所有非渲染交互（按钮、选择、参数）必须从 Web 起手，不在 omni.ui 里写最终 UI。
3. **三方协议统一信封**
   一种 Envelope `{type, ts, payload, request_id?}` 走遍 Web ↔ Backend ↔ Kit 三个边，不为不同链路设计不同消息格式。
4. **占位 → 真实分阶段**
   Phase 1 先用占位物理把通路打穿；后续阶段在不改协议的前提下替换 `state_engine.py` 内部实现。
5. **三维资产可重生**
   关键 USD 文件（`components.usda` / `earth_mesh.usda` / `orbit_line.usda` / `interior.usda`）通过 `tools/*.py` + `assembly_config.json` 可重生；手工微调只在专家用的 `gui_assemble.py` 滑块里发生。

## 2. 系统架构

### 2.1 三段式拓扑

```
┌──────────────────────┐
│  React Web App       │
│  ┌────────────────┐  │  WebRTC video + input  ┌──────────────────────┐
│  │ AppShell       │  │ ◄────────────────────► │ Omniverse Kit App    │
│  │  ├─ Router     │  │                        │  ┌────────────────┐  │
│  │  ├─ StreamMount│  │                        │  │ space.demo.*   │  │
│  │  ├─ DemoStore  │  │  WebSocket JSON        │  │  core / scene  │  │
│  │  └─ 5 Pages    │  │ ─────► commands        │  │  messaging/... │  │
│  └────────────────┘  │ ◄───── state_update    │  └────────────────┘  │
└──────────┬───────────┘                        └─────────┬────────────┘
           │  WS state_update (1 Hz)                      │ HTTP GET /state (5 Hz poll)
           ▼                                              ▼
   ┌──────────────────────────────────────────────────────────────┐
   │  FastAPI Backend (uvicorn :8001)                             │
   │  ┌──────────────────────────────────────────────────────┐    │
   │  │ ConnectionManager  ←  envelope dispatch              │    │
   │  ├──────────────────────────────────────────────────────┤    │
   │  │ StateEngine — async tick loop @ 1 Hz                 │    │
   │  │   sat (SatelliteState) · gs (GroundStationState)     │    │
   │  │   task · params · mode · camera_preset               │    │
   │  ├──────────────────────────────────────────────────────┤    │
   │  │ case_loader (data/cases/*)                           │    │
   │  └──────────────────────────────────────────────────────┘    │
   └──────────────────────────────────────────────────────────────┘
```

### 2.2 为什么不让 Kit 直接订阅 WebSocket？

Kit 自带 Python stdlib 没有 `websockets` 也没有 `aiohttp` 的 WS 客户端，引入会拖额外依赖。因此 Kit 走 **HTTP poll 5 Hz** + **单调钟本地插值**：

- 后端 1 Hz 是业务计算节奏；
- Kit `space.demo.scene._on_poll` 每收到一帧就更新一个 `_anchor_sim_s + _anchor_wall_s` 锚点；
- `_on_update` 每渲染帧用 `anchor + (now - anchor_wall)` 推算 sim_now，公式与后端完全一致（`_orbit_xyz`），让 SatelliteIcon 在轨迹线上**精确连续**而不是 1 Hz 跳着走。

如果后端的 `running` 翻转或 sim_time 跳变 > 1.5 s，强制重同步锚点。

### 2.3 Web 端单视频元素 + 路由穿透

WebRTC `<video>` 元素如果跟着 React Router 一起 unmount/remount，对应 MediaStream track 会被销毁，Kit 那边要重连——首次连接约 13 s，每次切页都这么久不可接受。

设计：

- [`StreamMount`](../web/src/components/StreamMount.tsx) 在 `AppShell` 里挂**一次**，绝对定位 `position: fixed`；
- 各页放一个 `<div id="scene-embed-slot">` 占位（[`SceneEmbed`](../web/src/components/SceneEmbed.tsx)）；
- StreamMount 用 `requestAnimationFrame` 轮询 slot 的 `getBoundingClientRect()`，把 `<video>` 的 left/top/width/height 同步上去；
- 没有 slot 时 `display: none`，视频还活着，连接还在。

这是设计的关键 trick；后果是 `<video>` 不在 React 树里、不接受 React props，状态完全靠模块级 `state` + `subscribeStreamStatus` 单例。

## 3. 数据模型设计

### 3.1 状态对象

定义在 [backend/models.py](../backend/models.py) + 前端 mirror [web/src/types/messages.ts](../web/src/types/messages.ts)：

```
SatelliteState
  id · orbit_type(LEO|SSO) · lat · lon · altitude_km · sunlit
  solar_input_w · payload_power_w · platform_power_w
  gpu_type(H100|H200|B200|MI300X) · gpu_utilization · temperature_c
  battery_soc · downlink_mbps · task_state(TaskPhase)

GroundStationState
  id · visible · rx_mbps · queue_depth

TaskState
  id · type · state(TaskPhase) · input_size_mb · result_size_mb
  progress · targets · alerts

Parameters
  orbit_type? · gpu_type? · load? · bandwidth_mbps? · inference_mode? · sunlit?

StatePacket
  sim_time_s · satellite · ground_station · task? · compare? · camera_preset · running
```

### 3.2 设计选择说明

- **TaskPhase 用字符串字面量**：`idle/created/capturing/inferencing/packaging/downlink/delivered`。前端按数组下标渲染 phase rail，约束顺序。
- **Parameters 全 Optional**：`set_parameters` 是部分更新；后端用 `model_copy(update=...)` 合并，避免每次都要传全量。
- **没有 `Position3D` 这种细分类**：lat/lon/altitude 直接是浮点。USD 端的 3D 坐标由 Kit 用相同公式重新算，**不**走协议——避免协议里塞跟单位 / 坐标系强耦合的字段。
- **`SatelliteState.task_state` 与 `TaskState.state` 同源但重复**：前者用于"卫星总体处于什么任务相位"，方便顶层卡片显示；后者是任务实体细节。这是冗余但显式的设计，省去 Web 端联表。

## 4. 通信协议设计

### 4.1 信封

```json
{ "type": "play|pause|state_update|...", "ts": 1713720000.123,
  "payload": { ... }, "request_id": "uuid4-only-when-needed" }
```

为什么所有消息共用一个信封：

- Web 一个 `ws.onmessage` 就够分发；
- 后端 `Envelope` 单一 Pydantic 模型 + 一个 `t == 'xxx'` 大 if-elif，逻辑集中；
- 日志只看 type 一栏就懂；
- 给 Kit 加新命令时不需要新模板。

### 4.2 频率与方向

| 流向 | 类型 | 频率 |
| --- | --- | --- |
| Backend → Web | `state_update` | 1 Hz 持续广播 |
| Backend → Web | `task_update` | 事件驱动（仅状态机迁移时） |
| Backend → Web | `selection_changed` / `camera_changed` | 命令回声 |
| Web → Backend | 所有命令 | 用户操作时 |
| Backend → Kit | 无（Kit 主动拉） | — |
| Kit → Backend | 无（目前未实现） | — |

### 4.3 错误处理

- 任何信封解析失败 → `error: {code:"bad_envelope", message:...}`；
- 未知 type → `error: {code:"unknown_type", message:t}`；
- `ack` 永远带 `request_id`，前端可以用 promise 化的 `send` 来等待（当前 store 没用，未来扩展点）；
- WS 断线 → 前端 2 s 后自动重连（[demoStore.connect](../web/src/store/demoStore.ts)）。

## 5. 前端设计

### 5.1 状态管理：Zustand 单 Store

`useDemoStore`（[web/src/store/demoStore.ts](../web/src/store/demoStore.ts)）是**唯一**的 UI 真理源：

```ts
ws · connected · lastState · task · selectedPrim · parameters
mode · cameraPreset · eventLog
+ connect/send/play/pause/reset/setMode/setParameters/startTask
+ selectObject/changeCamera
```

为什么不用 Redux / React Query：

- 唯一长连接 + 1 Hz 推送，没有缓存策略需要；
- 业务状态简单，4 行 reducer 足够；
- Zustand 的细粒度 selector（`useDemoStore(s => s.lastState?.satellite)`）天然避免 Card 全量重渲。

约束（在 [docs/ui_page_spec.md](ui_page_spec.md) 里冻结）：

- 禁止"每页一个 WebSocket"；
- 禁止把状态塞 URL params；
- 禁止前端推导物理（如自己积分轨道）。

### 5.2 五页布局

`AppShell` 用 CSS Grid 提供：

```
┌─────────────────────────────────────────────┐
│ header (brand · nav · clock · status · ▶❚❚⟲)│  56px
├──────────────────────────┬──────────────────┤
│                          │                  │
│  scene slot              │  side panel      │
│  (Outlet 内具体页面)      │  (cards/params)  │
│                          │                  │
├──────────────────────────┴──────────────────┤
│ bottom (timeline / eventlog / phase rail)   │
└─────────────────────────────────────────────┘
```

每页都按 `page page--{name}` 命名 class，CSS 在 [App.css](../web/src/App.css) 里集中定义。`StreamMount` 的 `<video>` 是 fixed 在所有页面之上的"自由元素"，靠 slot rect 对齐。

### 5.3 ECharts 计划

Phase 2 起每个图表是一个 `<ChartName Chart>` 组件，订阅 `lastState`，保留最近 N 秒环形缓冲在 store 之外的 `useRef`（避免反复触发 Zustand 订阅）。具体 spec 见 [docs/ui_page_spec.md §Shared components](ui_page_spec.md)。

## 6. 后端设计

### 6.1 单进程异步架构

[backend/app.py](../backend/app.py) 用 FastAPI `lifespan` 在启动时拉起一个 `StateEngine`，整个进程：

- 一个 asyncio 事件循环；
- `StateEngine._run` 协程 1 Hz tick；
- 每个 WS 客户端一个协程跑 `_handle` 循环；
- `ConnectionManager.broadcast` 用 `asyncio.Lock` 保护 client 集合，stale socket 自动剔除。

### 6.2 StateEngine 的内部模式

```python
class StateEngine:
    _on_state: Callable[[StatePacket], Coro]     # broadcast 回调
    _sim_time_s · _running · _sat · _gs · _task
    _mode · _params · _camera_preset
    _task_loop: asyncio.Task | None

    # 生命周期
    async start() / async stop()

    # 同步命令处理（mutator）
    play() / pause() / reset() / set_time() / set_parameters()
    set_mode() / set_camera_preset() / start_task(case_id)

    # 读
    snapshot() -> StatePacket

    # 内部
    async _run(): while True: sleep(1/HZ); if running: tick; await on_state(snapshot())
    _update_placeholder_physics(dt)
```

设计要点：

- 所有 mutator 是**同步**函数，只能从事件循环线程调用；通过 `await ws.send_json` 串行化网络写；
- `snapshot()` 用 `model_copy()` 复制，避免广播到序列化前被 tick 改飞；
- `on_state` 回调是构造时注入的 `broadcast_state`，所以 engine 不依赖 FastAPI——单元测试时可换桩。

### 6.3 物理 Phase 2 接入计划

`backend/services/` 现在是空 `__init__.py`。规划里要从原 Kit 大扩展（`exts/spacedc.digital_twin/physics/`，仍在 [c:\Workspace\SpaceDC\exts/](../../exts/)）迁移：

- `orbital_mechanics` — SGP4 / 二体；
- `solar_array_model` — 朝向 + 入射角 + 阴影；
- `thermal_model` — 节点热网络；
- `battery_model` — 容量 / 充放电曲线 / 老化。

接入接口：每个模型暴露 `tick(state, dt)` 函数，`StateEngine._update_placeholder_physics` 改写成一个依次调用的管线。

## 7. Omniverse 端设计

### 7.1 扩展拆分原则

按"关注点正交"拆 7 个扩展，每个扩展 ≤ 300 行（区别于原 `exts/spacedc.digital_twin/scene/satellite_builder.py` 1493 行的大反例）：

- **core** = bootstrap / 启动 Stage；
- **scene** = 全部动态行为（poll、Stage 切换、prim 投影）；
- **messaging** = NVIDIA 模板的消息桥，**不要**改它；
- **timeline** = sim clock 镜像；
- **selection** = 拾取事件；
- **camera** = 命名相机；
- **task_maritime** = 单一案例 overlay；

让 `scene` 当前承担了较多职责（poll + 切 Stage + 更新 icon + 绑相机），是 Phase 1 的合理过载——后续 `camera` / `selection` 接通后再把对应代码搬出去。

### 7.2 Stage 切换 vs sublayer

原方案考虑过把 overview/satellite/interior 做成 sublayer，按 `visibility` 开关；最终选择 `open_stage()` 完全替换：

| 维度 | sublayer 切换 | open_stage 切换（采用） |
| --- | --- | --- |
| 切换延迟 | 几乎瞬时 | 1–2 s（需 deferred 30 帧绑相机） |
| 资源占用 | 全部常驻 | 只占用当前 Stage |
| 复杂度 | sublayer 命名 / customLayerData 互相打架 | 简单 |
| 单位制冲突 | 100 km vs 1 cm 同 Stage 共存——爆炸 | 各 Stage 独立 `metersPerUnit` |

特别是 `metersPerUnit` 这一点决定性：geo overview 用 100 km/单位才合理，特写用 cm/单位才能用 NVIDIA Datacenter 资产。

### 7.3 SatelliteIcon 同步问题

Backend 算 lat/lon、Kit 算 (x,y,z)。两边公式必须严格一致：

```python
# 共用常量
ORBIT_RADIUS_UNITS    = 69.21   # ≈ (earth_radius + 550 km) / 100 km
ORBIT_INCLINATION_RAD = math.radians(60.0)
ORBIT_PERIOD_S        = 90.0    # demo period

theta = 2π * sim_time_s / ORBIT_PERIOD_S
x = R cos θ
y = R sin θ cos a
z = R sin θ sin a
```

设计选择：

- 共享公式而非共享数据。每秒只传 sim_time_s，三维由 Kit 自己根据时间算位姿——这样轨道线 USD 是静态的，icon 动态运行；
- 单调钟用 `time.monotonic()` 而非 `time.time()`，避免系统时钟跳变；
- 每次 `_on_poll` 重新锚定，可容忍 ≤ 1.5 s 抖动。

## 8. 启动与运维

### 8.1 一键启动脚本

[start_all.bat](../start_all.bat) 设计：

1. `taskkill /F /IM kit.exe` — 防止上次崩溃的 Kit 留下 49100 占用；
2. 三个 `start "..."` 各启一个独立 cmd 窗口（不是 `/B` 后台），用户能直接看日志；
3. 20 s `timeout` 让 Kit 完成首次资源加载再弹浏览器；
4. `popd` + `endlocal` + 最后 `pause`，关闭窗口前给一个停顿。

为什么不用 `docker compose`：

- Kit 必须在物理 GPU 上跑 RTX 渲染 + WebRTC 编码，无法容器化（至少在 dev 阶段）；
- 三个服务都是 dev 模式（uvicorn `--reload`、vite dev、Kit `killOnClientDisconnect=false`），统一编排意义不大。

### 8.2 环境变量

| 变量 | 用途 | 设置点 |
| --- | --- | --- |
| `SPACE_DEMO_USD_ROOT` | Kit 找 USD 的绝对路径 | `launch_kit.ps1` 自动设 |
| `SPACE_DEMO_BACKEND_HTTP` | scene 扩展轮询的后端地址 | 默认 `http://localhost:8001/state` |
| `SPACE_DEMO_INITIAL_STAGE` | core 扩展首开的 Stage 名 | 默认 `overview.usda` |
| `SPACE_DEMO_FOCUS` | 启动 focus 模式（保留） | `launch_kit.ps1 -Focus satellite` |
| `VITE_BACKEND_WS` | 前端 WS 地址 | 默认 `ws://localhost:8001/ws/state` |

### 8.3 Kit 模板生成自动化

[docs/kit_setup.md](kit_setup.md) 描述用 `--input` 隐藏参数把 NVIDIA `repo template new` 的交互 prompt 全自动化。生成 → 拷贝回 `ov_app/` → 用 [sync_to_kit.ps1](../ov_app/sync_to_kit.ps1) 反向同步到 `kit-usd-viewer-template/source/extensions/`。`viewer_streaming.kit` 因为 AutoInput 不能驱动 checkbox，是**手工**仿照 `default_stream.kit` 写的。

### 9.2 工具脚本设计

`tools/` 下脚本的共同模式：

- 顶部硬编码 `ROOT = Path("C:/Workspace/SpaceDC/space-compute-demo")`；
- 直接 print 字符串拼出 `#usda 1.0` 文本（不用 `Usd` API），因为这些是**配置驱动**生成器，pxr.Usd 在 venv 里没装；
- `gui_assemble.py` 用 Tkinter 是为了零额外依赖（venv 里不引 Qt）。

### 9.3 LUMID 卫星 vs Satellite_v022

历史上有两条卫星本体路径：

- Satellite_v022（自研 Inventor 出的 STL）— 由 `import_satellite_stl.py` 分类 bus/panel/dish/boom 并附 PBR。

当前 `assembly_config.json` 默认指向 `Satellite_v022.usdc`，LUMID 保留为备选。

## 10. 风险与权衡

| 风险 | 现状 | 缓解 |
| --- | --- | --- |
| Kit 启动慢 (≈13 s) 影响体验 | 一次性 | `start_all.bat` 20 s sleep；浏览器侧加 "connecting" 文案 |
| WebRTC `<video>` 与 React 路由冲突 | 已解决（StreamMount fixed 定位） | — |
| Backend 单点 / 无持久化 | 演示场景可接受 | 多实例 / SQLite 留到生产化阶段 |
| Kit poll 5 Hz 与 sim 1 Hz 错位 | 已解决（共享公式 + 锚点） | — |
| 占位物理与真实物理结果差异大 | 已知 | Phase 2 一次性整体替换，**不要**在占位上累积新业务 |
| metersPerUnit 单位制易踩 | 已通过 Stage 隔离 | 跨 Stage 的常量在代码里以 `_UNITS` 后缀命名，文档显式标 |
| Tkinter GUI 不跨平台 | 仅 dev 用 | 不参与 demo 部署 |
