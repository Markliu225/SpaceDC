# Kit App Setup

Our Kit app + `setup`/`messaging` extensions are generated by the NVIDIA `repo template new` flow. The tool is TTY-only by design, but it accepts a hidden `--input` arg that takes a `;`-delimited answer script — we exploit that for full automation.

## Fully automated generation (no interactive step)

```powershell
cd C:\Workspace\kit-usd-viewer-template

# 1. One-time: pre-accept EULA (else the first question is the EULA prompt)
New-Item -Path .\.omniverse_eula_accepted.txt -ItemType File -Force | Out-Null

# 2. Capture or regenerate playback.toml
$script = 'Application>;[omni_usd_viewer]: USD Viewer;space.demo.viewer;Space Compute Demo;0.1.0;space.demo.messaging;Space Demo Messaging;0.1.0;space.demo.setup;Space Demo Setup;0.1.0;No'
.\repo.bat template new --input $script --generate-playback C:\Workspace\SpaceDC\space-compute-demo\ov_app\playback.toml

# 3. Replay the playback to render files into source/
.\repo.bat template replay C:\Workspace\SpaceDC\space-compute-demo\ov_app\playback.toml
```

This produces:
- `source/apps/space.demo.viewer.kit`
- `source/extensions/space.demo.messaging/` (with NVIDIA `omni.kit.livestream.messaging` wiring)
- `source/extensions/space.demo.setup/`

Those get copied back to `ov_app/` as canonical source. `sync_to_kit.ps1` pushes them back out to Kit source before building.

## The `--input` trick explained

`REPO_TEMPLATE_SCRIPT` env var (or `--input` CLI arg) feeds `AutoInput` a `;`-delimited answer sequence. `AutoInput` handles `select` and `input_text` prompts; `checkbox` is **not** supported (that's why we say "No" to application layers rather than picking from the streaming-layer checkbox menu).

Answer sequence, in order:

| # | prompt | answer |
|---|---|---|
| 1 | initial `Application>/Extension>/Repository>` select | `Application>` |
| 2 | pick app template | `[omni_usd_viewer]: USD Viewer` |
| 3 | application_name (regex-validated) | `space.demo.viewer` |
| 4 | application_display_name | `Space Compute Demo` |
| 5 | version | `0.1.0` |
| 6 | messaging ext name (first linked extension) | `space.demo.messaging` |
| 7 | messaging ext display | `Space Demo Messaging` |
| 8 | messaging ext version | `0.1.0` |
| 9 | setup ext name | `space.demo.setup` |
| 10 | setup ext display | `Space Demo Setup` |
| 11 | setup ext version | `0.1.0` |
| 12 | "add application layers?" | `No` |

Linked extension order comes from `sample_templates.toml`: messaging is listed first (`type=extra`), then setup.

## Streaming layer (hand-authored)

Because `AutoInput` can't drive the layers checkbox, the streaming layer is NOT added via `template new`. Instead `ov_app/apps/space.demo.viewer_streaming.kit` is hand-authored (modelled on `templates/apps/streaming_configs/default_stream.kit`). It depends on `space.demo.viewer` + `omni.kit.livestream.app` and is the entry point launched by the web client.

## Build

```powershell
cd C:\Workspace\kit-usd-viewer-template
.\repo.bat build
```

First build: 10–15 min (downloads Kit SDK, carb plugins, python, precaches extension registry).

## Launch

```powershell
# viewer (local window)
.\_build\windows-x86_64\release\space.demo.viewer.bat

# streaming viewer (exposes WebRTC on 127.0.0.1:49100)
.\_build\windows-x86_64\release\space.demo.viewer_streaming.bat
```

Once the streaming variant is running, the web UI's `SceneEmbed` will connect automatically.
